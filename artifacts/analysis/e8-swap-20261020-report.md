# E8 — Swap-capacity boundary, two concurrent Task06_Lung jobs

**Result (20 October 2026):** At the same outer 8 GiB RAM and parent 6 GiB RAM, Normal completed neither two-job attempt at any tested swap cap from 0 through 2,048 MiB. SRCG completed both jobs in both zero-swap repetitions. One of three SRCG attempts at 1,024 MiB stopped on the experiment's admission-stall watchdog; it did **not** OOM or exhaust swap. Thus the lowest **tested successful** cap is **0 MiB for SRCG (2/2 attempts)**. No successful Normal cap was found within 0–2,048 MiB. Neither statement is a guaranteed minimum or a prediction for other workloads.

[Per-run CSV](e8-swap-20261020-runs.csv) contains every valid run's completion, kernel limits, OOM kills, RAM/swap peaks, swap-limit events, swap I/O, memory pressure, observed duration, successful makespan, wait count, steps, and model digests. Raw logs and 50 ms cgroup traces are in `artifacts/e8-swap-20261020/<run>/` (excluded from Git because they are large). Each `result.json` is the machine-readable summary. The first `normal-0m-r1` directory is an **invalid setup pilot**: systemd rejected a textual 8 GiB limit before training. It is excluded; `normal-0m-r2` and `r3` are the two valid zero-swap repetitions.

## Definitions and controlled configuration

- **Outer RAM/swap cap:** the transient systemd service containing the experiment; `memory.max=8 GiB`, `memory.swap.max` set to the row's swap cap. **Parent:** its `srcg` cgroup containing both jobs; `memory.max=6 GiB`, `memory.swap.max` equal to the outer swap cap. **Job:** each training cgroup; `memory.swap.max` also equal to the row's cap. This is *not* twice the available swap: the shared parent cap constrains both siblings together. Normal's job RAM cap is 6 GiB each, with the shared 6 GiB parent enforcing the aggregate. SRCG starts each job at a 2 GiB base RAM quota and has 2 GiB shared **Reserved Memory** available for temporary quota borrowing; host headroom admission threshold is 1 GiB. SRCG's RAM admission/borrowing code was not changed for E8.
- **Training:** two concurrent processes, same Task06_Lung 63-volume dataset, 3D U-Net (base width 32), volume tensor 32×128×128, batch size 1, 63 steps/job, one epoch, six DataLoader workers/job, prefetch factor 2, pin memory off, shuffle on, non-persistent workers, AdamW learning rate 0.0001 and weight decay 0.0001, seed 42, CUDA, no checkpoint. Both methods use the same training program and model. “Normal” means this normal PyTorch training path placed by the SRCG CLI into cgroups for measurement, **without** the reservation manager or SRCG batch admission; it is not an uninstrumented process outside cgroups.
- **Completion:** both jobs reach step 63, emit `epochs_complete`, exit successfully, and yield the expected final model tensor SHA-256 `3502fe809eb9d75055dab6c4bc5fa0a032bc850a09d711deb3e427c76882767e` for each job. All completed jobs in this study matched it, including single survivors of failed Normal attempts. A failed attempt's elapsed time is *not* compared to a successful makespan.
- **OOM kill:** kernel `memory.events:oom_kill` increment. **Swap-limit exhaustion:** parent swap reaches its `memory.swap.max` and `memory.swap.events:max/fail` increment; it can accompany an OOM kill. **Admission stall:** no training step progress for 45 s plus at least ten `reserved_memory_exhausted` WAIT decisions, after which the watchdog stops the attempt. This is an operational timeout, not proof of permanent deadlock or OOM. **Memory pressure:** cumulative cgroup PSI `some/full` stall time. **Swap I/O:** cgroup `memory.stat` `pswpin/pswpout` counts in pages. **Thrashing:** severe repeated swap I/O with sustained progress loss; a few swaps or a swap-cap OOM alone do not establish it.

The host had `/dev/zram0` swap, a 4,294,963,200-byte active partition (about 4 GiB), priority 100; its virtual disk size was 4,294,967,296 bytes, compression algorithm `zstd`. `/proc/meminfo` reported 4,194,300 KiB total swap and at least 4,193,564 KiB free at every preflight. zswap was disabled (`N`); `vm.swappiness=60`. Host swap was **never changed**. Because this is compressed **RAM-backed zram**, these results must not be generalized to disk swap latency or independent disk capacity. Host global swap I/O counters are in the CSV as supplementary figures; unrelated host activity can contribute to them. Kernel: `7.2.9-arch1-1`; Python 3.14.8; PyTorch 2.13.0+cu130; NVIDIA driver 615.78.08, RTX 4050 Laptop GPU. The raw `environment.txt` for each run records exact host/GPU state, boot ID, and Git commit.

The kernel-reported `memory.swap.max` was the exact configured byte value at the **outer, parent, and both job** levels in all 25 valid attempts. Each `init.log` also confirmed outer `memory.max=8,589,934,592` bytes and parent `memory.max=6,442,450,944` bytes. Parent `memory.swap.peak` never exceeded the configured parent cap. The parent cap, not a per-job sum, is the aggregate enforcement point. The trace also records sibling `swap.current`, but its sequential, non-atomic reads can differ from a single simultaneous snapshot by a few pages; it is **not** used to prove the aggregate bound. For example, two Normal traces near the cap showed a sampled sibling sum 16–40 KiB above the cap while the authoritative parent swap peak remained exactly at the cap.

## Failure mechanism and transition finding

- Normal at **0 MiB**: RAM-only parent OOM; zero swap and zero swap-limit events. At **256–2048 MiB**, parent swap reached exactly its cap on every run, `memory.swap.events:max` and `fail` rose, and the kernel OOM-killed processes. This is **cgroup OOM with swap-limit exhaustion**, not an admission WAIT. Normal at 1,024 MiB lost both jobs in both repetitions; at other caps one job survived, but no attempt completed both.
- SRCG at **1,024 MiB, repetition 2**: both jobs reached step 56/63, then produced no further step for 45 s while the manager logged `reserved_memory_exhausted` WAIT. The watchdog ended the attempt after about 129 s observed duration. There were **zero OOM kills, zero swap-limit events, and only 0.14 MiB parent swap peak**, so increasing swap is not a supported explanation for this failure. The same cap succeeded in repetitions 1 and 3; 1,536 MiB succeeded 3/3; 2,048 MiB succeeded 3/3. This is a real observed admission-policy inconsistency, not a monotonic swap failure→success transition.
- No Normal failure→full-completion interval exists **within the tested 0–2,048 MiB range**. SRCG succeeds already at the lower bound, 0 MiB. An intermediate 1,536 MiB cap was tested three times, alongside three repetitions each at 1,024 and 2,048 MiB, to investigate the isolated outcome change. These data do **not** justify claiming a guaranteed swap threshold.
- Normal's high-cap runs did substantial swap I/O: at 2,048 MiB, the parent recorded 176,109–227,471 page-ins and 461,035–501,850 page-outs, with 1.61–1.71 s cumulative full memory pressure. But those runs ended by OOM **at the swap cap**. No run timed out solely due to swap thrashing, so thrashing is not claimed as a separate primary failure cause.

## Reproduction and scope

From the repository root, use `bash benchmarks/dataloader_policy/run_e8_swap.sh normal 512 1` (or `srcg`); the arguments are method, swap MiB, and repetition. The runner refuses a pre-existing output directory, checks host swap free capacity before every run, creates equal cgroup swap caps, records live kernel readings, and stops an admission stall without changing host swap. Use new repetition numbers on rerun. The raw run directory includes `environment.txt`, `cgroup-trace.jsonl`, both training logs, `summary.txt` where training reached cleanup, `e8-runner.txt`, and `result.json`. Regenerate the CSV with `python benchmarks/dataloader_policy/export_e8_swap_csv.py --raw-dir artifacts/e8-swap-20261020 --output artifacts/analysis/e8-swap-20261020-runs.csv`.

Only one host, one model/dataset, and this two-job workload were tested. Run order was not randomized, so page cache and background load may affect time; completion and kernel-limit evidence are the main claims. This E8 study **does not add swap control to SRCG** and does not claim that giving Normal more than 2 GiB swap could never work.
